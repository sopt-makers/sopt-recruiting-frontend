# 리크루팅 QA 자동화 — 문제 정의와 해결 설계 (마스터 플랜)

> 이 문서는 SOPT Makers 리크루팅 서비스의 QA 개선 작업의 기준점이다.
> 여러 차례 전제가 뒤집히며(어드민의 실제 능력 발견, 페이지 간 상태 불일치 발견) 재정의를 거친 최종 버전이다.
> 모든 결정은 추측이 아니라 코드/네트워크/실데이터로 검증된 근거를 갖는다.

---

## 0. 이 문서가 다시 쓰인 이유

처음 문제를 "상태가 너무 많아 QA가 지옥이다"로 잡았고, 해결책으로 "MSW 시나리오 + 기획자 패널"을 세웠다. 그러나 작업을 진행하며 두 개의 전제가 무너졌다.

첫째, **어드민의 실제 능력을 과소평가했다.** 처음엔 "기간·유저상태를 백엔드에 매번 요청해야 한다"고 가정했으나, dev 어드민이 별도로 존재하고, 기간·기수·YB/OB뿐 아니라 **합격 상태(applicationPass/finalPass)까지 드롭다운으로 설정 가능**함을 네트워크 탭으로 직접 확인했다(`recruiting-admin/applicant/pass-status`). 즉 "기획자가 특정 상태를 눈으로 보는 것" 상당 부분은 이미 어드민으로 가능했다.

둘째, **코드를 직접 읽으며 실제 버그 후보 두 개를 발견했다.** (1) `MyResponse.applicationPass`가 타입상 `boolean`인데 실제 코드는 `== null` 분기를 쓰는 타입 드리프트, (2) 같은 상태에서 `MyPage`와 `ResultPage`가 다르게 반응하는 불일치.

이 두 발견이 작업의 무게중심을 바꾼다. "기획자 수동 QA를 돕는 패널"에서 **"어드민이 구조적으로 못 하는 것 — 자동화·시각제어·회귀검증 — 을 채우는 개발자 하네스"**로.

## 1. 문제 재정의

### 1-1. 표면 문제 (처음 보이는 것)

리크루팅 서비스는 하나의 코드베이스로 두 조직(SOPT/makers)을 다루고, 지원→마감→서류발표→면접→최종발표라는 타임라인을 따라 같은 화면이 계속 다른 얼굴을 보인다. 여기에 유저 상태(미지원/임시저장/제출/서류합격/불합격)가 곱해져, 검증할 화면이 수십 가지로 불어난다.

### 1-2. 구조적 실체 (코드로 확인한 것)

이 수십 가지는 사실 **세 입력의 조합**이다.

- `season`(날짜 뭉치) — `/latest` 응답
- `myInfo`(submit/hasDraft/applicationPass/finalPass) — `/my` 응답
- 현재 시각 — `new Date()`

화면 분기는 이 셋을 비교·조합한 순수 함수(`useRecruitingSchedule`의 5개 `NoMore*` 플래그 + `renderApplicationStatus`)의 결과다. 즉 상태가 많은 게 아니라 **입력이 셋**이다.

### 1-3. 진짜 문제 (어드민 발견 이후 정밀화)

어드민이 세 입력 중 둘(날짜, 유저 상태)을 통제할 수 있음이 밝혀진 이상, 문제를 정확히 좁혀야 한다. 진짜 남은 문제는 넷이다.

1. **시각 경계의 재현 불가.** "마감 1분 전", "면접이 끝나는 바로 그 순간" 같은 경계 타이밍은, 어드민으로 날짜를 맞춰도 실제 시계가 흘러가 딱 잡기 어렵다. 이 경계가 하필 버그가 가장 자주 나는 곳이다.
2. **회귀의 자동 검증 부재.** 어드민은 "사람이 한 번 눈으로 보는 것"까지다. 코드가 바뀔 때마다 8 phase × 5 user × 2 page의 조합을 자동으로 재검증하는 수단이 없다. 매 기수 인수인계로 사람이 바뀌면 이 부담은 리셋된다.
3. **공유 dev 환경의 충돌.** 어드민으로 상태를 바꾸면 dev DB 전체가 바뀌어, 동시에 QA하는 팀원끼리 서로의 상태를 덮어쓴다.
4. **sopt 접근 불가.** sopt 어드민 권한이 없어, sopt 화면은 어드민 경로로는 QA 자체가 불가능하다. (라우팅이 makers와 달라 검증이 꼭 필요함에도.)

그리고 이 문제들과 별개로, 이미 발견된 **실제 버그 두 개**(타입 드리프트, 페이지 불일치)를 닫아야 한다.

### 1-4. 한 문장 정의

> 리크루팅 화면 분기는 (season, myInfo, now) 세 입력의 순수 함수다. 어드민은 이 중 날짜·유저상태를 통제해 "수동 확인"을 가능케 하지만, 시각 경계·자동 회귀검증·팀 격리·sopt는 구조적으로 못 한다. 이 빈틈을 코드 레벨 검증 하네스로 채우고, 그 과정에서 드러난 상태 로직의 결함을 바로잡는다.

## 2. 대안 비교 (각 결정마다 깊게)

### 결정 A — 무엇으로 상태를 통제할 것인가: 어드민 vs 시드 데이터 vs MSW

이게 가장 근본적인 갈림길이다. 세 대안을 실제 능력 기준으로 비교한다.

| 기준 | dev 어드민 | dev DB 시드 스크립트 | MSW (가짜 응답) |
|---|---|---|---|
| 날짜 통제 | O (수동, 절대값) | O (스크립트) | O (자동, 상대값) |
| 유저 상태 통제 | O (드롭다운, 확인됨) | O | O |
| 시각(now) 고정 | X | X | X (별도 clock 필요) |
| 상대 시간("오늘-1일") | X | 스크립트로 가능하나 번거로움 | O |
| 자동화 테스트 연동 | X (사람이 클릭) | △ (setup 느림, DB 의존) | O (테스트마다 격리 주입) |
| 팀원 간 격리 | X (공유 DB) | X (공유 DB) | O (브라우저 로컬) |
| sopt 커버 | X (권한 없음) | X (권한/접근) | O (프론트만) |
| 실서버 계약 검증 | O (진짜 응답) | O | X (가짜라 계약은 못 봄) |
| 셋업 비용 | 낮음 (이미 있음) | 중간 | 중간 |

**해석.** "사람이 한 번 눈으로 보는 수동 QA"만 놓고 보면 **어드민이 이미 충분하다.** 날짜도 유저상태도 바꿀 수 있으니, 패널을 새로 만들 강한 이유가 없다. 이 사실을 인정하는 것이 이번 재정의의 핵심이다.

그러나 **자동화·격리·상대시간·sopt** 네 축에서 어드민과 시드는 구조적으로 막힌다. 특히 자동화 테스트는 "테스트마다 독립된 상태를 빠르게 주입하고 끝나면 원복"이 필수인데, 공유 DB에 의존하면 병렬 실행이 깨지고 느려진다. MSW는 네트워크 응답만 가로채므로 각 테스트가 완전히 격리된다.

**결정:** 자동화 검증의 상태 통제는 **MSW**. 단, 실서버 계약 검증(프론트-백 약속이 안 깨졌나)은 MSW가 못 하므로, 그건 별도의 얇은 실백엔드 스모크 or OpenAPI 계약 테스트로 분리한다(이 레포는 이미 OpenAPI 스펙·타입 생성 파이프라인 보유).

**근거의 조직 적합성:** 우리는 (a) sopt 어드민 권한이 없고, (b) 매 기수 인수인계로 회귀 자동화가 절실하고, (c) 팀이 동시에 QA하는 상황이 잦다. 세 조건 모두 MSW의 격리·자동화 강점과 정확히 맞물린다.

### 결정 B — 기획자 패널을 만들 것인가

처음엔 "기획자가 백엔드 없이 상태를 재현"이 패널의 존재 이유였다. 그러나 어드민으로 기간·유저상태를 다 바꿀 수 있음이 확인된 지금, 패널의 명분은 **약해졌다.** 정직하게 인정한다.

남은 패널의 가치는 두 가지로 좁혀진다.
- **시각 경계 재현:** 어드민이 못 하는 "오늘 기준 마감 1분 전"을 패널+clock으로 즉시. (어드민 대비 유일 우위)
- **조합 갤러리:** 8×5 조합을 한 화면에 그리드로 띄워 "전체를 한눈에" 훑기. 어드민은 한 번에 하나만 본다.

**결정:** 패널은 **만들되 역할을 좁힌다.** "어드민 대체"가 아니라 "어드민이 못 하는 시각제어 + 전체 조합 갤러리"로. 순수 상태 재현(합격 유저 하나 보기 등)은 어드민에 맡긴다. 우선순위는 자동화(단위/E2E)보다 낮춘다. 만약 만들다가 시각제어·갤러리의 실효가 약하다고 판단되면 과감히 접는다.

**근거의 조직 적합성:** 기획자가 이미 어드민에 익숙하다면 패널 학습 비용이 낭비다. 그래서 "어드민으로 안 되는 것만" 패널이 담당하는 게 중복을 피하는 유일한 정당화다.

### 결정 C — 테스트 무게중심: E2E 중심 vs 단위 중심

참고한 네이버파이낸셜 사례는 E2E 자가개선 루프를 최대로 끌어올렸다. 그 팀의 근거는 "AI로 PR이 폭증해 검증이 병목"이었고, 220+ 페이지 대규모였다. 우리 맥락은 다르다 — 크리티컬 플로우가 소수고, 팀이 작고, 매 기수 사람이 바뀐다.

| 층위 | 무엇을 검증 | 비중 | 근거 |
|---|---|---|---|
| 단위/컴포넌트 | phase×user 조합별 문구·분기 (순수함수) | **가장 두껍게** | 조합 폭발을 싸고 완전하게 흡수. 순수함수라 결정론적 |
| 프론트 시나리오 E2E | 실제 클릭 플로우(로그인→작성→제출→확인)가 이어지나 | 얇게 | 페이지 간 경계·라우팅은 단위가 못 잡음 |
| 실백엔드 스모크 | 프론트-백 계약이 안 깨졌나 | 최소 | 시즌 직전만. MSW가 못 보는 영역 |

**결정:** "Not too many, mostly integration"(Guillermo Rauch) 원칙대로 **단위 두껍게, E2E 얇게.** 네이버식 자가개선 루프·위험도 스코어링은 지금 규모엔 과하므로 접는다.

**근거의 조직 적합성:** 유지보수 비싼 E2E를 많이 깔면 다음 기수에게 부채가 된다. 팀 규모와 인수인계 주기가 이 선택을 강제한다.

### 결정 D — E2E에서 무엇을 모킹하나 (네이버와 반대)

네이버는 "백엔드까지 모킹하면 E2E 의미가 옅어진다"고 했다. 그들의 목적이 실서버 전구간 검증이기 때문이다. 우리 목적은 다르다 — **"프론트가 season/myInfo를 올바로 해석하는가"**가 리스크다.

**결정:** 우리 프론트 E2E는 **입력(season/myInfo)을 MSW로 일부러 고정**한다. 검증 대상이 프론트 분기 로직이므로 입력을 통제하는 게 정답. 실서버 계약은 결정 A대로 별도 스모크로 뺀다.

**근거:** "무엇을 검증하려는가"가 모킹 경계를 정한다. 우리는 프론트 해석을 보므로 입력 고정이 맞다. 좋은 원칙도 목적이 다르면 반대로 적용해야 한다.

### 결정 E — org(sopt/makers)와 group(YB/OB)을 시나리오 축에 넣나

코드로 확인한 사실:
- `org`은 빌드타임 상수(`__IS_MAKERS__`, `--mode`로 결정). 런타임에 못 바꿈. 라우팅 자체가 다름(makers는 AuthPage만, sopt는 풀 라우트).
- `group`은 `season`에 실려 오는 런타임 값이나, 상태분기 화면(MyPage/ResultPage/ReviewPage)에선 안 쓰이고 `useGetQuestions`(질문 API)에만 쓰임 — grep으로 확인.

**결정:** `Scenario = { phase, user }`. org는 시나리오 밖 **테스트 실행 축**(withMode로 두 모드 다 검증). group은 상태분기 무관이라 지금 범위에선 제외(ApplyPage 질문 QA를 다룰 때 재도입).

**근거:** 축은 "화면 상태를 실제로 가르는 것"만. 코드로 확인해 넣고 뺐다.

## 3. 확정된 도메인 모델 (코드 검증 완료)

### phase 8단계 (useRecruitingSchedule의 5개 NoMore* 조합 경계)

`notStarted → applying → waitingScreeningResult → screeningResult → interview → afterInterview → finalResult → ended`

`interview`/`afterInterview`는 `NoMoreReview`(interviewEnd 기준, 지원서 열람 가부)가 갈리는 지점이라 분리.

### user 5단계 (MyResponse 필드 조합)

`none`(hasDraft:false) / `draftOnly`(hasDraft:true,submit:false) / `submitted`(submit:true,applicationPass:null) / `screenPass`(applicationPass:true) / `screenFail`(applicationPass:false)

### buildSeason 타임스탬프 배치 표 (설계 확정, 구현은 아직)

`daysFromNow(offset)` 기준 offset. 8개 phase 모두 같은 "간격 모양"을 유지한 채 전체 타임라인을 슬라이드해서 `now`(offset 0)가 목표 구간에 오도록 만든다. gap은 makers 37기 실데이터(서류접수 8/14~15, 서류발표 8/20~22, 면접 8/23~24, 최종발표 8/27~28) 기준 대표값 — 정확한 일수가 아니라 "경계 전/후" 재현이 목적이라 기수마다 다른 gap에 집착하지 않는다.

- 지원마감(AE) ~ 서류발표시작(RS) gap: **5일**
- 서류발표종료(RE) ~ 면접시작(IS) gap: 1일
- 면접종료(IE) ~ 최종발표시작(FS) gap: **3일** (최초 설계안 5일에서 실데이터 기준 수정)

| phase | applicationStart | applicationEnd | applicationResultStart | applicationResultEnd | interviewStart | interviewEnd | finalResultStart | finalResultEnd |
|---|---|---|---|---|---|---|---|---|
| notStarted | +2 | +7 | +12 | +13 | +14 | +16 | +19 | +20 |
| applying | -2 | +3 | +8 | +9 | +10 | +12 | +15 | +16 |
| waitingScreeningResult | -6 | -1 | +4 | +5 | +6 | +8 | +11 | +12 |
| screeningResult | -10 | -5 | 0 | +1 | +2 | +4 | +7 | +8 |
| interview | -13 | -8 | -3 | -2 | -1 | +1 | +4 | +5 |
| afterInterview | -15 | -10 | -5 | -4 | -3 | -1 | +2 | +3 |
| finalResult | -17 | -12 | -7 | -6 | -5 | -3 | 0 | +1 |
| ended | -19 | -14 | -9 | -8 | -7 | -5 | -2 | -1 |

`interview`/`afterInterview`는 다른 6개 타임스탬프가 완전히 동일하고 `interviewEnd`만 now 기준 앞/뒤로 바뀜 — `NoMoreReview` 경계를 정확히 겨냥.

### 발견된 결함 두 개 (닫음 — 6번에서 최종 판정)

1. ✅ **타입 드리프트:** `MyResponse.applicationPass`가 타입은 `boolean`, 실제 사용은 `== null`. → 3번에서 `boolean | null`로 수정 완료, dev 실응답도 확인. 종결(백엔드 문의 불필요).
2. ✅ **페이지 불일치:** 최종발표 기간+applicationPass가 true 아닐 때, MyPage는 "서류 불합격" 표시 / ResultPage는 전면 차단. → 아래 "6번 결론"에서 버그로 확정. 심각도 낮음, 조치는 11번(상태 머신 리팩터링)으로 이관.

### 6번 결론: 발견 결함 최종 판정

**대상 1 — applicationPass 타입 드리프트:** 종결. 3번에서 처리 완료, 백엔드 문의 불필요.

**대상 2 — finalResult × submitted/screenFail 불일치**

실제 사용자 여정을 코드로 추적 완료:
1. `MyPage/index.tsx` 118·125번 줄: `StatusButton(to="/result")`이 finalResult phase에서도 노출되어 실제 클릭 동선이 존재.
2. `ResultPage/components/ScreeningResult.tsx`: `pass=false`일 때 완결된 "서류 불합격" 안내문이 이미 존재하지만, 이 컴포넌트는 `NoMoreScreeningResult` 게이트에만 묶여 있어 finalResult phase에선 렌더 자체가 안 됨.
3. MyPage와 ResultPage가 각각 독립적으로 게이트를 재판단하는 구조라, MyPage가 보여준 정보(문구)와 ResultPage의 실제 접근 가능 여부가 어긋남.

**판정:** 버그 (의도된 설계 아님).

**원인:** `ScreeningResult` 게이트(`NoMoreScreeningResult`)와 최종발표 차단 게이트(`NoMoreFinalResult`)가 독립적으로 설계되어, "서류 결과는 최종발표 기간에도 계속 조회 가능해야 한다"는 요구가 누락됨.

**심각도 재평가(하향 확정):** 낮음. 정상 지원 플로우 기준으로 재검토한 결과:
- 이 경로를 타려면 (a) 최종발표 기간까지 서류결과가 확정 안 된 극소수 케이스이거나, (b) 이미 서류에서 떨어진 사람이 최종발표 기간에 재방문해 버튼을 클릭하는 드문 경우여야 함.
- 대다수 지원자(서류 합격자)의 정상 경로는 영향 없음.
- 서비스 중단·데이터 손실 없음 — "정보 미노출" 수준.

**조치(최종):** 지금은 수정하지 않음 — 지원 기간(8월) 임박 + 낮은 심각도 + 낮은 발생 빈도 + 단독 수정 시 오히려 리스크. 11번(상태 머신 리팩터링) 시 `deriveRecruitingState`가 아래 규칙으로 통합하도록 설계에 반영:
- 서류 결과는 `NoMoreScreeningResult` 이후 최종발표 기간과 무관하게 항상 조회 가능해야 함.
- 최종 결과는 서류 합격자에 한해 `NoMoreFinalResult` 이후 조회 가능.
- 이 둘은 배타적이 아니라 누적적이어야 함.

## 4. 해결 리스트 (재정의판)

이전 리스트에서 **패널을 후순위로 내리고, 상태 머신 개선을 정식 항목으로 추가**했다. 이미 한 2번 산출물은 그대로 재사용된다.

**0. 근거 로그 문서** — 각 결정의 대안 비교·수치·스크린샷을 계속 축적 (이 문서가 그 시작).

**1. ✅ 환경 준비** — 브랜치, 구조 확인. 완료.

**2. ✅ Scenario 타입 + 유틸** — `types.ts`(phase 8/user 5), `dateUtils.ts`(상대날짜), `withMode.ts`(빌드모드 축). 완료.

**3. ✅ buildSeason / buildMyInfo** — 시나리오→가짜 season/myInfo. `src/mocks/scenario/buildSeason.ts`, `src/mocks/scenario/buildMyInfo.ts`로 구현 완료. `RecruitingResponse['season']`(비-yb/ob prefix 제네릭 필드) 형태로 반환 — `useRecruitingSchedule`이 실제로 소비하는 타입 기준. 8개 phase 전부 NoMore* 파생 로직으로 역산해 자기 자신으로 복원됨을 스모크 확인(임시 테스트, 커밋 안 함).

**확인 완료: 버그 아님.** `api-spec.yml`(`/recruiting-season/latest` 예시)과 기존 `src/mocks/handlers.ts` fixture는 `ybApplicationStart`/`obApplicationStart` 식 prefix 필드를 쓰는 반면, `RecruitingResponse['season']` 타입과 `useRecruitingSchedule`은 prefix 없는 제네릭 필드를 읽는다 — 처음엔 세 번째 타입 드리프트 후보로 의심했으나, dev `/latest` 실응답을 네트워크 탭으로 직접 확인한 결과 실제로는 prefix 없이 온다. `api-spec.yml`의 해당 예시가 (아마 과거 admin 원본 응답을 캡처한) 오래된 문서일 뿐, 실제 계약과는 무관. `yarn api-spec`으로 스펙 재생성 완료 — 백엔드 확인 대기 아님, 종결.

**4. ✅ MSW 핸들러 시나리오 기반 개편** — `src/mocks/handlers/{scenario,auth}.ts` + `src/mocks/scenario/state.ts`(get/set/resetScenario 진입점)로 구현 완료. `/latest`, `/my`가 시나리오 주입식으로 동작.

**5. ✅ 단위 테스트 (가장 두껍게)** — `src/tests/views/MyPage.test.tsx`, `src/tests/views/ResultPage.test.tsx`. phase(8)×user(5) 매트릭스로 MyPage 지원상태 분기(40케이스)·ResultPage 렌더 분기(40케이스) 잠금, 총 80케이스 전부 통과. finalResult×submitted/screenFail의 MyPage-ResultPage 불일치(결함 #2)를 현재 실동작 그대로 회귀 고정 — 판단은 6번에서. ReviewPage는 draft/questions builder가 별도로 필요해 이번 범위에서 제외(후속 항목).

**6. ✅ 발견 결함 정리** — 최종 판정 완료("6번 결론" 참고). 대상1(타입 드리프트)은 종결. 대상2(finalResult×submitted/screenFail 불일치)는 버그로 확정했으나 심각도 낮음(대다수 정상 플로우엔 영향 없음, 정보 미노출 수준)으로 재평가 — 지원 기간 임박·단독 수정 리스크를 감안해 지금은 보류하고 11번(상태 머신 리팩터링)으로 조치 이관.

**7. Playwright + codegen 골든패스** — 로그인→작성→제출→확인 1개. 얇게.

**10. .claude/skills 도메인 문서** — 규칙·시나리오 인코딩. AI 생성 품질 + 인수인계 겸용.

**11. 상태 머신 리팩터링 (하이라이트)** — `deriveRecruitingState(season, myInfo, now)`로 상태를 한 번만 계산해 페이지들이 단순 매핑만 하도록. 5번 테스트를 안전망 삼아 진행 → 페이지 불일치 구조적 제거. "테스트로 현재 동작 박제 → 리팩터 → 회귀 없음 증명"의 완결 서사.

**12. (나중) 실백엔드 스모크 / AI 확장** — 계약 검증, Generator 등. 근거가 생길 때만.

## 5. AI 활용 — 근거 생길 때만

현재까지 AI 활용은 "Claude Code에 질문·답변" 수준이며, 멀티에이전트·자가개선 루프 같은 건 지금 규모엔 과하다. 억지로 넣지 않는다. 대신 근거가 실측되는 지점에서만 도입한다.

- **5번:** phase×user×page ≈ 80칸 매트릭스. 사람이 채우면 누락(실제로 notStarted/waitingScreeningResult를 초기에 누락). → "AI 열거 시 누락 0"을 실측하면 도입 근거.
- **7번:** codegen+AI 정리 vs 수동 작성 시간 측정 → 근거.
- **10번 이후:** 도메인 문서 유무에 따른 AI 생성 테스트 통과율 차이 측정 → "맥락 주입 효과"를 직접 실증(네이버의 에이전트 온보딩 주장 검증).
